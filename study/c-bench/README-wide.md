# IBLT_Cplusplus：64 / 128 / 160 位 key benchmark

将上游 `IBLT_Cplusplus` 扩展为完整的 128 位和 160 位 key，并在同一 WASM 模块里保留原始 uint64 版本作为基线。
这是本地改造版，不是上游现成提供的 128/160 位 API。其他库没有在本次扩展位宽。

## 运行与构建

```sh
npm run bench:wide:check
npm run bench:wide
```

若尚未构建，先按 [C/WASM 说明](README.md) 安装 Emscripten 并下载固定版本源码，再执行：

```sh
npm run bench:c:build      # 正确性检查使用之前的原始 64 位模块做交叉验证
npm run bench:wide:build
npm run bench:wide:check
npm run bench:wide
```

参数示例：

```sh
N=10000 DIFF=100 CELLS=200 TRIALS=30 WARMUPS=5 npm run bench:wide
```

默认写入 `c-bench/results-wide.json`，可用 `OUTPUT` 指定其他文件。

## 如何扩展 key

`build-wide.py` 从固定 commit 的上游源码生成两个改造版本：

- key、keySum 和结果 key 类型从 uint64 改成 `std::array<uint8_t, 16/20>` 的封装。
- XOR、相等比较、结果集合排序和序列化处理全部字节。
- MurmurHash3 输入从 8 字节扩展为完整 16/20 字节，仍保持上游的 4 个桶哈希和 seed。
- keyCheck 保留上游的 **32 位校验和**；key 位宽增加不意味着校验强度也变成 128/160 位。
- 复制、插入、删除、相减和 peeling 流程保持上游实现，value 长度仍为 0。
- 构建目录头文件增加只用于传输访问的 friend。原始 vendor 源码不修改，生成代码可直接审查。

128 位可以无损存两个 uint64 时间戳；160 位可以无损存完整 SHA-1。不会将宽 key 哈希/截断到 uint64 后再存储。
也没有将一个 key 拆成多个独立集合元素。

## 数据和计时

每轮生成同一批 SHA-1 摘要，64/128/160 位分别使用前 8、前 16、完整 20 字节。
这是为了让各宽度具有类似的数据分布，**不是上一轮的时间戳数据集**。
所有实际宽度都检查唯一性，数据并非把 64 位 key 补零到宽 key。
SHA-1 计算和输入转换均在计时之外。

- 两端各 10,000 条，共享 9,950 条，各自独有 50 条，总差异 100。
- 三种宽度都使用 **200 桶、4 个哈希**。
- 预热 5 轮，正式 30 轮；轮换执行顺序，每轮新数据。
- **fresh**：双方全量构建、序列化/反序列化、相减、解码并将结果复制回 JS。
- **maintained**：表跨轮保留，每端删除旧的 50 条独有 key、添加新的 50 条，再传输、相减和解码。
  两端共 200 次单 key 变更；首次构建不计时。
- 计时不包括输入拷贝到 WASM、模块初始化、销毁及正确性断言，没有真实网络或浏览器测试。
- C++ 接口采用批量插入/删除。完整计时拆分与每轮原始结果写在 JSON 中。
- 表内每桶的 wire format 是 `i32 count + N 字节 keySum + u32 check`，整数小端，无压缩。
  不含协议头或参数协商。实际 payload：200 × (N + 8) 字节。

## 正确性检查

`check-wide.mjs` 验证：

- 前 64 位相同、最后一个字节不同的宽 key 能分别恢复。
- 所有字节位置分别非零的 key 都能恢复，涵盖 64 位以上的所有位置。
- 全零、全 1 key、增删、复制隔离、相等集合差分和序列化往返。
- 原始 64 位模块与新基线的同一集合生成完全相同的二进制表。

benchmark 每轮都对照真实差集检查全部 key 字节、方向、数量与重复项。
增量场景每轮额外重建两张表，与持续维护的表逐字节比较；验证工作不计时。
如果出现未解码完成或报告成功但 key 错误，保留原始结果并以非零退出码结束，不跳过失败样本。

## 本机结果

Node.js v24.21.0，Linux x64，Intel Core Ultra 7 258V，Emscripten 4.0.23，`-O3`。
以下为中位数，时间单位 ms；每个宽度的两个场景均 **30/30 成功**，无错误差集。

| key 位宽 | 首次构建＋同步 | 复用表、更新＋同步 | Payload |
|---|---:|---:|---:|
| 64 位原版 | 3.2479 | 0.1290 | 3,200 B |
| 128 位改造版 | 3.8925 | 0.1466 | 4,800 B |
| 160 位改造版 | 4.7558 | 0.1543 | 5,600 B |

相对这次的 64 位基线，128 位完整流程增加约 20%，160 位增加约 46%。
传输量分别增加 50% 和 75%；增量流程仍在约 0.15 ms 量级。
位宽改变也会改变桶映射和 peeling 顺序，因此这不是完全隔离哈希图结构的逐指令比较。
绝对耗时会受 JIT、调度、频率和 GC 影响；样本不能证明生产环境永不解码失败。

对应文件：`wide-key.h`、`build-wide.py`、`wide-wrapper.cpp`、`wide-bridge.mjs`、`benchmark-wide.mjs`。
